# Capestone_Flipkart
End-to-end E-commerce Decision Intelligence pipeline built from scratch in Python (NumPy). Covers statistical hypothesis testing, logistic churn modeling, K-means customer segmentation, and neural architecture analysis .


Domain: E-commerce

# Flipkart Decision Intelligence: my capstone write-up

Hi! This repo is my capstone for the Minor in AI. The setting is a customer-analytics team at Flipkart with three open questions: *is our average-order-value assumption still right, which customers are about to leave, and what kinds of shoppers do we actually have?* Everything here runs offline with plain Python and NumPy, and the data is synthetic (generated by the script in this repo), so please read the numbers as "what the method does on this data", not as anything about the real company.

A quick note on how I worked: every number quoted below was copied from a file in `outputs/`, and those files are produced by the scripts, nothing is typed in by hand. I also re-ran the whole pipeline from a fresh copy of the folder and diffed the outputs against the committed ones; they were identical. All money is in INR.

## How to run

From a clean clone, in this order:

```bash
pip install -r requirements.txt
python generate_data.py     # should print: 800 10 170 c6f249ba693f1ebeed318d6d5e18de23
python part1.py
python part2.py
python part3.py
python part4.py
```

`common.py` is a small helper file (data loading, the 560/240 split, logistic regression, KNN, metrics) that `part2.py` and `part4.py` both import. It only defines functions, so importing it never re-runs anything. Each script writes its files into `outputs/`.

## Part 1 findings

**Is the INR 800 planning assumption still right? (R1.1)** No. The sample mean is 8.9382 (about INR 894) with a standard error of 0.3243, giving z = 2.8930. That is beyond the critical value of 1.96, so I reject H0 (μ = 8.0) at α = 0.05. The 95% interval is 8.3026 to 9.5738, so the whole interval sits above 8.0. A Type I error here would mean telling the planners "your INR 800 is wrong" when it is actually right, and getting them to rewrite category plans for nothing. The gap is 0.9382 column units, roughly INR 94 per order or about 12% above plan. I think that is worth acting on if order volumes are large, since it adds up, but I'd also stay cautious: the standard deviation (9.1723) is bigger than the mean, so order values are very skewed, and a few big baskets are pulling the average up. Statistically significant and practically important are not automatically the same thing.

**How much data would we need? (R1.2)** To pin the average down to ±0.5 units (INR 50) at 95% confidence we need `n_required` = 1293 orders, and we only have 800. With 800 rows our margin of error is about 0.64 (roughly INR 64), so the planning team should collect around 500 more observations before treating the average as tight enough.

**Gradient descent vs the closed form (R1.3)** `gd_slope_gap` came out at 0.0000 (it has to be below 0.001, and it is). Squared-error cost is a single smooth bowl with exactly one lowest point, so with standardised X4 and a sensible step size, gradient descent just rolls down to the same line the formula gives (the cost was already flat at 40.3698 by update 100).

**Is there a funnel? (R1.4)** Yes, in the raw model. `resid_sd_ratio_raw` = 3.7525: the residual spread in the upper half of fitted values (8.6891) is almost four times that of the lower half (2.3155), so errors grow as predicted order value grows. Taking logs fixes it: `resid_sd_ratio_log` = 1.0396, i.e. nearly equal spread (0.5165 vs 0.5369).

**Which predictors matter, and do they earn their place? (R1.5)** Using the mechanical rule |coefficient| > 0.05, the predictors in the Task 1.7 model are ln(X4) (1.1576), X2 complaints (0.0940), X3 discount share (0.1067) and X6 cash-on-delivery flag (0.1518). X1 tenure (−0.0074), X5 loyalty (0.0028) and X7 plus-member (0.0172) fall below the line. I want to be honest that this is just a threshold, not a ranking: the coefficients are in different units, so a tiny per-month tenure effect can still add up over years, and I wouldn't read this list as "the only things that matter". On the question of whether the extra predictors earn their place: adjusted R² goes from 0.6561 (log-log with just ln(X4)) up to 0.7403 with all seven. That is a real improvement, even after the penalty for more predictors, so yes.

## Part 2 findings

**Learning rates (R2.1)** From lowest to highest loss after 200 updates: η = 1.0 (0.3703), η = 0.1 (0.3776), η = 0.01 (0.5091). A rate that is too small (0.01) simply hasn't travelled far enough yet, while the large one got furthest in the same number of steps; on this smooth, standardised problem even η = 1.0 stayed stable, though that isn't guaranteed in general.

**What drives churn? (R2.2)** The three largest absolute weights are X3 discount share (0.9013), X1 tenure (−0.5554) and X2 complaints (0.5505). The biggest odds ratio is X3 at 2.4629: for customers who differ by one standard deviation in how much of their buying is discounted, the heavier-discount customer has about 2.5 times the odds of churning, with everything else held fixed.

**Accuracy is misleading here (R2.3)** A model that says "nobody churns" is right 0.7875 of the time on the test set (`blind_accuracy`), and my logistic model at τ = 0.5 scores 0.8042, barely better, while missing 27 of the 51 real churners. So accuracy hides the thing we care about. Dropping τ from 0.5 to 0.3 lifted recall from 0.4706 to 0.7451 (24 → 38 churners caught) at the price of lower precision, 0.5455 → 0.4634. Accuracy actually fell to 0.7625, which is *below* the blind model, and that's fine, because we're deliberately accepting more false alarms to catch more churners.

**Logistic vs KNN (R2.4)** At τ = 0.3 the logistic model has F1 = 0.5714 and recall = 0.7451. KNN (K = 5, picked by 5-fold CV) managed F1 = 0.3696 and recall = 0.3333. Logistic is clearly better, and it also lets me move the threshold, which KNN's majority vote doesn't.

**What would I deploy? (R2.5)** The logistic model at **τ = 0.15**, the cheapest threshold on the training rows. On the test rows that costs INR 6,050, compared with INR 11,800 at the default 0.5 and INR 20,400 if we flag nobody. I chose the threshold on training rows because the test rows have to stay untouched to give an honest final check; if I tuned τ on them, the cost I report would be flattering.

## Part 3 findings

**Choosing K (R3.1)** The WCSS drops are: 2→3: 659.8282, 3→4: 108.0739, 4→5: 171.0575, 5→6: 45.5466. The biggest cliff is going from 2 to 3 clusters, and by the elbow rule from the brief the first K where the next drop is less than half the previous drop is K = 3 (108.07 < 0.5 × 659.83). The drops do not shrink steadily (4→5 is bigger than 3→4), and that is a side-effect of the pinned starting rows: they give one reproducible solution, not necessarily the global optimum. I used K = 3 as the brief asks.

**Segments (R3.2)** Using `part3_segments.csv`:

| Segment | Size | Tenure | Complaints | Discount share | Avg order value | Loyalty | Churn rate | Mean order value |
|---|---|---|---|---|---|---|---|---|
| A | 322 | 47.5 | 1.95 | 0.225 | 12.5 | 62.2 | 0.0186 | 3.60 |
| B | 255 | 28.6 | 6.07 | 0.453 | 28.7 | 55.0 | 0.2353 | 17.12 |
| C | 223 | 14.4 | 4.23 | 0.712 | 16.5 | 38.5 | 0.4664 | 7.29 |

- **A: "Steady loyalists"** (long tenure, few complaints, rarely use discounts, churn rate only 0.0186). Action: leave them alone with discount spend; protect them with a simple loyalty-points or early-access perk instead.
- **B: "Big baskets, big frustrations"** (biggest orders, most complaints, churn rate 0.2353). They look premium in spend, though not in satisfaction. Action: a service-recovery step, such as a proactive call or priority support, after a complaint.
- **C: "Bargain-hunting newcomers"** (shortest tenure, highest discount share, lowest loyalty). This is the segment with the highest `outcome_rate`, **0.4664**. Action: a retention coupon in the first months, ideally paired with a nudge toward a second full-price purchase.

C matches the "bargain-focused" shopper from the brief. I'd be careful calling A "premium loyal", because their order values are actually the lowest, so I named them from the numbers. The data has no dates, so I can't say anything about seasonal shoppers.

**Dendrogram cuts (R3.3)** Single linkage cuts into **4 clusters**: {E1}, {E2, E3, E6}, {E4}, {E5}. Complete linkage cuts into **2 clusters**: {E1, E4, E5} and {E2, E3, E6} (average linkage agrees with complete). They disagree because single linkage only looks at the *closest* pair, so groups chain together cheaply (its last merge is at 3.4, so no big gap appears at the top and the largest gap falls earlier). Complete linkage looks at the *farthest* pair, so the two natural groups only merge at 7.9, which creates one huge, obvious gap.

**PCA (R3.4)** The mean vector is all zeros after standardising, as expected. PC1 explains 0.5227 of the variance and is basically an "established vs discount-driven" axis: positive loadings on tenure X1 (0.5317) and loyalty X5 (0.4418), negative on discount share X3 (−0.5187), complaints X2 (−0.4100) and average order value X4 (−0.2916). Two components reach 0.7593, so we need **3 components** to keep at least 80% (0.8616). The segment means on PC1 are A = 1.7773, B = −0.7831, C = −1.6709: the segments line up along PC1 in order, and C, the highest-churn group, sits at the extreme negative end.

## Part 4 findings

**Best split (R4.1)** S4 (tenure ≤ 24 months) wins by both information gain (0.1252) and Gini gain (0.0606). It splits the 560 training rows into 188 customers of whom 86 churned (about 46%) and 372 of whom 33 churned (about 9%), so it separates the groups better than the other three questions. A tree grown until every leaf is pure would overfit, because to get pure leaves it has to memorise individual quirks and noise, which won't repeat on new customers. A simple fix is to cap the depth (or require a minimum number of customers per leaf).

**Which model to ship (R4.2)** The plain logistic model. In the like-for-like comparison at τ = 0.3 it has F1 0.5714 and recall 0.7451 (in production I'd use the money-based τ = 0.15 from Part 2). The one-question stump was close (F1 0.5532, recall 0.7647), but soft voting (0.5507 / 0.7451), hard voting (0.5344 / 0.6863) and KNN (0.3696 / 0.3333) didn't beat it. So combining models did not help here: KNN is much weaker than the other two, and voting with a weak member pulls the group down.

**AdaBoost by hand (R4.3)** After round 1 the two misclassified points (3 and 7) carry a total weight of **0.5000** (0.2500 each). Round 2 trusts h2 more (α₂ = 0.8047 vs α₁ = 0.5493) because, on the re-weighted points, h2 only makes an error of 0.1667, and it gets exactly the two hard points that h1 got wrong.

**Network sizing (R4.4)** Model A, option 2 (the CNN), nothing trained, just counted:

| Layer | Output shape (H × W × D) | Parameters |
|---|---|---|
| Input | 28 × 28 × 1 | 0 |
| conv 5×5, 6 filters, pad 2 + ReLU | 28 × 28 × 6 | 156 |
| max-pool 2×2, stride 2 | 14 × 14 × 6 | 0 |
| conv 5×5, 16 filters, pad 0 + ReLU | 10 × 10 × 16 | 2,416 |
| max-pool 2×2, stride 2 | 5 × 5 × 16 | 0 |
| flatten | 400 | 0 |
| dense 32 + ReLU | 32 | 12,832 |
| dense 10 (output) | 10 | 330 |
| **Total** | | **15,734** |

For comparison the plain 784 → 16 → 16 → 10 network has 13,002 parameters. A fully connected layer on a 128 × 128 × 3 image into 1,024 neurons needs 50,332,672 parameters, while a 3×3 convolution with 64 filters on the same image needs only 1,792, which is why convolutions scale.

Model B (RNN): W_xh is 128 × 64, W_hh is 128 × 128 and W_hy is 16 × 128, giving `rnn_total` = 26,768 parameters. It doesn't grow with longer reviews because the *same* weights are reused at every time step; a longer sequence just means more repeats, not more weights.

For ten product categories I'd use ReLU in the hidden layers and a softmax output with categorical cross-entropy loss.

Why very deep plain networks stall: during backpropagation the gradient is multiplied by many small factors layer after layer, so by the time it reaches the early layers it has almost vanished and they barely learn. A skip connection adds a direct "shortcut" path around a block, so the gradient can flow straight back and the early layers keep receiving a useful signal.

## Model-choice memo

**To:** Head of Retention  **Re:** Which churn model to ship

I recommend the logistic regression model with an alert threshold of **0.15**.

On the 240 held-out customers, that threshold costs INR 6,050 in coupons and lost margin, versus INR 11,800 at the default 0.5 and INR 20,400 if we flag nobody (`part2_results.txt`). That is about 70% less than doing nothing. I picked 0.15 using training rows only, so the test figure is an honest check.

I compared alternatives in `part4_voting.csv`. KNN was the weakest (F1 0.3696, recall 0.3333). Neither voting scheme beat the plain logistic model (F1 0.5714 at τ = 0.3 against 0.5344 for hard voting and 0.5507 for soft voting). Using the same cost rule at τ = 0.3, the logistic model costs INR 7,400 and the one-question tenure rule INR 7,350. That is almost the same, but the tenure rule is too coarse to rely on, and the logistic model gets cheaper still at 0.15.

The main risk is that the test set holds only 51 churners, from a single split, so each churner we miss moves the cost by INR 400 and the exact threshold may not carry over. The INR 50 and INR 400 figures are also rough estimates; if the real coupon cost changes, the best threshold will too.

Neither Model A (product pictures) nor Model B (review text) should be built before this structured model is in production, since the churn signal already sits in our tabular columns and both need data we don't have here.

## Limitations

1. **The data is synthetic.** It comes from a script, so the clean three-group structure is partly baked in. Real Flipkart data would be messier, and none of these numbers describe the real business.
2. **One split, few positives.** Everything in Parts 2 and 4 is judged on a single 560/240 split with only 51 churners in the test set. A shift of one or two customers changes the cost by INR 400 to INR 800, and the best K and best threshold are only valid for this split.
3. **The threshold was tuned on training rows.** The cost-based τ = 0.15 was chosen from in-sample probabilities on the same rows the model was trained on, rather than cross-validated, so it may be slightly optimistic or unstable.
4. **The costs are assumptions.** INR 50 per false alarm and INR 400 per missed churner are rough figures from the brief; the answer is sensitive to them, and I haven't done a sensitivity check.
5. **The z-test assumes things that are only roughly true.** Order values are heavily skewed, and I treated the sample SD as the true SD. With 800 rows the test is probably fine, but the conclusion about a gap of about INR 94 should be double-checked with more data.
6. **No time dimension.** Without dates I can't test for seasonal shoppers, or check whether a model trained on one period holds up in the next.
7. **Models A and B are only paper sizing.** I counted parameters but didn't train anything, so I can't say how well those models would actually perform.
